## Implemented boundaries

- `EncodedVideoOutput` owns one hardware H.264 encoder, pre-encoded SDK source/track, independent 60 FPS handoff pacer, codec-safe frame identity, and bitrate/keyframe feedback. It rejects invalid/non-increasing timestamps and bounds outstanding identities at 16; it never silently evicts an accepted encoded reference frame. A handoff/backlog failure is explicit. The synthetic media probe now uses this component for both exact video qualities. Diagnostic metadata corruption remains a probe-supplied transform; recording/pixel analysis remain in the tools directory.
- `TrackReader` owns a bounded video or stereo audio stream and its reader thread. `ShareReceiver` moves stream creation/removal to an owned control thread: SDK delegates only enqueue commands. It bounds commands at 16, active readers at eight, decoded video at two buffers and audio at eight buffers. Reader/creation errors close admission and surface as errors. Stop rejects late attachments, discards pending commands, closes streams and joins outside the admission mutex. Application callbacks must be bounded; a callback that blocks forever cannot be cancelled by this wrapper.
- `ShareModel` is a Qt list model for owner/share/generation and the two video qualities plus optional audio. Track names use `gs1.<32 lowercase hex digits>.<16 hex generation digits>.<1080|720|audio>`. Owner identity comes from the SDK participant. Unknown protocol, malformed/noncanonical identity, wrong media kind/source/dimensions, clear publications, duplicate quality conflicts and reassigned SIDs are rejected. A fresh generation clears old associated tracks; stale remove/retire events cannot erase its replacement. Explicit retirement leaves a tombstone until participant removal. Entries are bounded at 64, including tombstones. The integration must retire a generation when its logical share ends; this model alone does not infer a remote Stop command.
- `RoomController` provides asynchronous Qt join/leave, explicit subscriptions, validated publication announcements, late-join discovery, owner cleanup and room epochs. SDK operations run on an owned transport thread; join/leave commands do not wait for SDK network work on Qt. Commands are bounded at 64 and outstanding Qt notifications at 256; subscription catalog storage is bounded at 192. A new join requires a client-held 32-byte key, configures GCM and enables its manager. Ready means room/key setup, **not** per-track encryption readiness. Generic worker commands are a bridge for subsequent integration, not a complete share lifecycle.

The room controller closes command admission on reconnect/disconnect or local encryption errors. It emits invalidation and requires explicit leave/rejoin; it does not automatically resume old publications. The future publisher must own and stop its capture/encoding/audio workers, gate every real-content handoff and repeat readiness before recovery. Merely receiving a Qt notification later is insufficient for that immediate media gate. Destructor cleanup can wait for SDK shutdown; normal leave is asynchronous.

The existing media probe now exercises the extracted hardware output and receiver. The stereo probe uses the extracted receiver for track-based audio, including actual WASAPI playback and wrong-key checks. Its direct `fromParticipant` case remains an independent SDK API regression. These probes still use controlled synthetic content and their own transport setup. They do not establish actual capture, rendering or public Internet performance.

## SDK defect found by integration

The first controller run joined and left eight times successfully, but its encrypted publication announcement never reached the model. Source inspection showed `Room::onFfiEvent` moving `rpublication` into the remote participant map and then assigning the moved-from pointer to `TrackPublishedEvent::publication`. The callback therefore received an empty pointer. The patch retains a shared reference for both map and event.

The wrapper also adds `Room::remotePublicationSnapshot()`, copying initial publication references and owner identities under the room lock used for event updates. This avoids iterating `RemoteParticipant::trackPublications()` concurrently with SDK events. The controller serializes snapshot ingestion with its own event catalog; later unpublish/participant events update the copied catalog. A late viewer discovers an existing publication without depending on a new publish event.

Both changes live in `scripts/prepare_livekit_wrapper.py` and the pinned C++ patch; the wrapper build manifest now hashes `room.h` as well. The Rust/FFI engine has not changed in this increment. SDK and app were rebuilt, and original SDK/failed reports remain intact. Current C++ patch SHA-256 is `5bd6c22c27c2c5f908f630f7ca1e963654399f2a51d9e7f13d73064e37dfc777`; wrapper DLL `cd499a68c05abe5cee25bb7f43e0607614dfd7796e608ca9454bd240f98ad67c`; engine DLL remains `288132e619e0e30b7ad273d49cdf2441c8c63eca789a52cfb1a52662d24c7924`. 4. Integrate actual WGC/WASAPI capture, conversion/scaling and receiving/rendering/playback into the UI in the subsequent steps. Manual quality selection must coordinate keyframes/subscriptions and continuous audio; raw subscription commands alone do not provide that UX.
5. Retain the user's upload preference: bitrate reduction first, protect audio, and pause 1080p only as a last resort under sustained insufficient uplink. Define measured thresholds/hysteresis and restore with headroom. Automatic fallback is still planned, not implemented.
