# Cryptor parser repair

Date: 2026-10-21, Europe/Budapest. Scope: the valid H.264 round-trip failure recorded in [the previous cryptor report](20-fail-closed-cryptor.md). All content and hostile inputs are synthetic. The UI remains a local capture preview; no game, SSH/VPS service or unrelated app is modified.

## Cause and repair

The [exact pinned upstream source](https://raw.githubusercontent.com/webrtc-sdk/webrtc/89d790b/api/crypto/frame_crypto_transformer.cc) escapes the video ciphertext, IV and trailer together. Its receiver reads IV bytes using offsets into the still-escaped packet and only then unescapes the ciphertext. Timestamp/SSRC byte patterns requiring an escape can therefore supply the wrong IV to authentication. The repair normalizes the entire encrypted tail before locating the trailer and IV. AES-GCM, its authentication tag, key derivation and nonce generation are retained.

The pinned source SHA-256 is `a0ad0713525437fd53dd23127e10a093442a4e7f827f22bd0b54907626c582da`. Its header matches the installed header after newline normalization, SHA-256 `c9215ff1d839adce5147f75e31f6a229cc36d2cfaef6bbfe44aeab19f74f84f9`; preparation rejects a mismatch. `scripts/prepare_frame_cryptor.py` verifies the original hash and creates the reviewable [upstream-source patch](../patches/webrtc-89d790b-frame-crypto.patch), retaining attribution.

The receiver also checks the decoded tail contains a complete tag, IV and trailer before indexing or allocating from lengths. Codec-header lengths use `size_t` instead of wrapping at 255 bytes; incomplete NAL headers are rejected. Upstream INFO statements that print raw keys/derived material are removed from this recompiled translation unit. No keys, payloads or media are included in test diagnostic logs.

The existing strict policy remains in force: server plaintext trailers cannot bypass authentication, disabling a cryptor permanently revokes new work, and the app requires per-owner/SID/generation readiness. These parsing changes must not enable any plaintext fallback or treat a failed tag as a valid frame.

## Integration and controls

The first integrated engine build failed with duplicate symbols because Rust bundles the static WebRTC objects. This is preserved in [the failed build log](../artifacts/cryptor-parser-engine-build.log). The build now makes a dedicated archive copy, removes exactly `obj/api/crypto/frame_crypto_transformer/frame_crypto_transformer.obj`, checks the member count, and compiles the repaired translation unit into the SDK bridge. A link anchor requires that replacement object. The pristine pinned archive is checksum-verified and retained for original-behavior controls. No duplicate-symbol suppression or permissive linker override is used.

The new native executable compiles the same generated source used in the SDK and links the remaining pinned library. It tests valid encrypted input before and after hostile inputs, with a completion sentinel and worker teardown instead of an arbitrary no-output sleep. Cases include the original small-RTP timestamp, timestamp wrap/escaped SSRC, headers over 255 bytes, missing keys, tampering, truncation, short headers/trailers, sticky disable/re-enable, and 128 additional deterministic malformed inputs per strict case.

The old native executable continues linking the pristine archive. Its original failed edge results remain valid historical evidence; repaired-source tests must not be assigned to that binary or used to rewrite older snapshots. The focused test operates at the encoded cryptor boundary, not a codec decoder or display. Real SDK forwarding and independent decoded-content checks are separate tests.
