# CPU and memory footprint

Date: 2026-10-20. Low CPU and memory use is now an explicit primary requirement alongside low latency. This is a bounded resource increment within step 2, not completion of the integrated app. The Qt app still previews local capture; room sharing, rendering and actual capture publication remain unfinished.

## Changes

- The audio input worker waits on a stop-aware condition variable instead of polling every 2 ms. Accepted audio wakes it immediately; close/Stop wakes it without waiting for another block. The 100 ms input capacity/age limits and per-handoff encryption checks are unchanged.
- An idle joined `RoomController` waits for a command or shutdown notification. Its 5 ms media pump runs only while a publisher is starting/sharing. Connection setup retains its bounded polling until the SDK connection result arrives.
- Both synthetic black startup canvases are released when all outgoing encryption handlers become ready, and on Stop/failure. Previously `clear()` on Stop kept vector capacity until publisher destruction, and active shares retained the startup canvases. At the exact NV12 sizes these buffers occupy **4,492,800 bytes (4.28 MiB)**. Diagnostics now verify zero retained priming capacity after readiness and cleanup. This is an allocation reduction, not a promise of an identical drop in process working set/private bytes: allocators and the GPU driver may retain other memory.
- `scripts/process_footprint.py` samples only existing handles from test-owned subprocesses every 250 ms, with bounded sample storage. It records process CPU time, logical CPU count, private committed bytes, resident working set and handles separately. `test_share_publisher.py --profile-resources` samples the synthetic client separately from its loopback SFU. Test executions now retain the probe executable hash and check it did not change during execution.

## Measurements and checks

The machine has 12 logical CPUs and a GTX 1070. CPU percentage means process CPU time divided by wall time and 12; one fully occupied logical CPU is about 8.33%. Core equivalents are also retained. Sampled memory peaks can miss shorter allocations. The middle diagnostic window excludes the first five and last two sampled seconds; it is not an exact media-phase marker.

The synthetic client is **one sender plus one receiver decoding BOTH 1080p and 720p**, stereo audio and pixel inspection in one process. Video encodes through NVIDIA hardware; its SDK receiver reports FFmpeg software decoding. There is no actual WGC/WASAPI capture, Qt rendering, Internet path or three-share workload in these samples. Encoded recording retention is disabled for resource comparisons, and Python/load-driver CPU and memory are excluded. A normal viewer will subscribe to one quality per share; its actual footprint must still be measured.

- [Original 30-second baseline](../artifacts/20261020-214011-share-publisher/summary.json), [client resource trace](../artifacts/20261020-214011-share-publisher/stereo-footprint.json): middle-window **9.39% CPU / 1.126 core equivalents**, peak private committed **245.41 MiB**, peak working set **162.58 MiB**. SFU CPU was 0.71%. Media passed, 59.23/59.70 inspected FPS, Stop 206.50 ms. This ran the previous publisher binary, whose existing source/executable snapshot is [retained here](../artifacts/20261020-publisher-completion-provenance.json); this run predates the new per-run executable hash field.
- [First event-driven 30-second run](../artifacts/20261020-214219-share-publisher/summary.json), [client resource trace](../artifacts/20261020-214219-share-publisher/stereo-footprint.json): **9.50% CPU / 1.140 core equivalents**, peak private **245.63 MiB**, peak working set **154.30 MiB** in the middle window. Media passed, 59.35/59.61 inspected FPS, Stop 205.66 ms. These figures do **not** establish an overall CPU/memory saving over baseline. This run preceded priming-buffer release. Handles rose from 1,758 to 2,012 around 12 seconds, then fell to 1,694 during teardown; that trace does not establish a permanent leak or explain the earlier lifecycle growth failures.
- [Final all-eight publisher suite](../artifacts/20261020-214557-share-publisher/summary.json) passed, including wrong key, audio off, missing handler, partial rollback, both cancellation paths and revocation. Priming-buffer capacity is zero after readiness and Stop. Short-case rates are diagnostics, not five-minute sustained acceptance.
- [Idle room and owned publisher test](../artifacts/20261020-214647-room-controller/summary.json) passed eight room cycles, publication/subscription cleanup, restarts, cancellation, a wake of the waiting audio worker and Stop. During **10 seconds of joined idle room**, whole-process CPU averaged **0.039% / 0.00469 cores**; the next queued command completed in **1.66 ms**. The harness's 1 ms inspection heartbeat is suspended during that measurement. This includes SDK background work but no GUI/capture/rendering, and has no before-change idle comparison. Maximum owned publisher Stop was 210.93 ms.
- [250 ms video-owner pause](../artifacts/20261020-214720-share-publisher/summary.json) passed with unchanged audio bounds: **502 audio blocks**, mailbox high-water **10 ms**, no expired audio, 15 raw video pairs replaced. Independent decoding verified 286 content frames plus five priming frames per quality with zero mismatches. This intentionally stalled run is not a clean-path rate benchmark or full A/V sync test.
- [Native checks](../artifacts/footprint-ctest.log) passed all four tests. [Sampler self-check](../artifacts/20261020-214647-footprint-self-check.json) cross-checked an owned 48 MiB allocation and CPU workload: sampled CPU time exactly matched the child's independent `time.process_time()` reading (2.03125 seconds), and observed private allocation increased by 54.55 MiB including interpreter overhead.

[The final 60-second sample](../artifacts/20261020-214739-share-publisher/summary.json), with [client](../artifacts/20261020-214739-share-publisher/stereo-footprint.json) and [SFU](../artifacts/20261020-214739-share-publisher/sfu-footprint.json) traces, passed on the priming-release build. 1080p averaged **59.23 inspected FPS**, 720p **59.70 FPS**, with zero inspected pixel/metadata/dimension errors; input-to-decoded p95 was **46.79/39.82 ms** and Stop took **205.98 ms**. Middle-window client CPU was **9.61% / 1.153 core equivalents**; peak private committed memory was **238.14 MiB**, peak resident working set **151.38 MiB**. SFU CPU was **0.42%**, peak private **80.01 MiB** and resident **58.16 MiB**. Client handles started and ended that window at **1,767**, with peak 1,769, and fell to 1,369 during sampled teardown. These are short observations; the CPU result does not demonstrate a saving versus the 30-second baseline, and different-duration memory peaks are not a controlled estimate of improvement.

[Resource validation and frozen source/runtime provenance](../artifacts/20261020-footprint-validation.json) link this increment's passing checks without superseding any historical failure. The previous five-minute run remains evidence for its previous frozen build; no new five-minute or stability-soak pass is claimed here.

## Remaining work

Set numerical resource budgets from the integrated client on target hardware. Profile idle, sender only, viewer of one selected quality per share, and simultaneous sharing/viewing separately. Prioritize verified hardware decoding, GPU scaling/rendering, reusable media buffers and fewer CPU readbacks/copies where measurements support them. Current capture and encoder input still make CPU copies; do not call them zero-copy.

Earlier intermittent lifecycle handle/thread growth and startup pixel corruption remain open in [the publisher report](14-share-publisher.md). Short resource samples do not satisfy the 60-minute stability gate. No claim is made that polling removal fixes SDK resource ownership, that all attempted tests passed, or that three concurrent shares can yet meet the target footprint/rate. The subsequent [managed-receiving increment](16-managed-receiving.md) implements bounded owner/generation receive ownership; SDK/network backlog age, congestion recovery and actual UI integration remain unfinished. Keep low latency, variable delivery below the default 60 FPS, audio protection and encryption readiness intact while optimizing.

All fixtures are local and bounded. Only fixture-owned processes are stopped; existing applications/services, games and the VPS are untouched. No game injection, game-memory access, hooks, overlays or custom drivers were added.
