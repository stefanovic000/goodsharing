# End-to-end encryption

Status: mandatory fail-closed requirement, explicitly reaffirmed by the user on 2026-10-21. Native feasibility tests are in progress. No claim of audited application security or a proven zero-failure probability.

## Mandatory failure behavior

Screen pixels and shared audio must never fall back to plaintext when E2EE is missing, not ready, disabled, invalidated or failed. Block real content before publication until every required track in the current owner/share generation has verified readiness. If readiness is lost, revoke content admission and stop the share with a visible error; do not retry by disabling encryption. Synthetic black/silence preroll is the only permitted startup input before content readiness.

Receiving must authenticate/decrypt each frame and bind admission to the expected owner, current generation and exact track SID. Failures must block new video presentation and audio playback, invalidate pending content and clear/mute the affected presentation. Reconnects, quality switches and rekeys must establish fresh readiness before resuming. Presentation/playback must recheck the current permission when consuming queued media; an earlier callback check alone is insufficient. Previously authorized and already delivered content cannot be recalled.

There must be no user setting, automatic bandwidth fallback or production application path that disables these checks. Raw diagnostic/unencrypted harness modes must remain isolated from shipped sharing/viewing paths. Ciphertext and signaling may still traverse the server during failure; the requirement is that no unencrypted captured content is sent and no unauthenticated media is exposed to viewers.

This is a release blocker, not a statistical allowance for occasional leakage. Passing current gated wrong-key tests is necessary but insufficient: earlier raw-SDK wrong-key tests detected unexpected known-audio output and remain unresolved in [the publisher evidence](14-share-publisher.md). Root-cause investigation, startup/failure/rekey/reconnect coverage, in-flight/queued-media revocation checks and the real capture-to-presentation path must be verified before claiming this requirement satisfied. The current UI remains a local capture preview; real capture publication and final presentation/playback integration are not complete.

LiveKit C++ SDK 1.12.3 exposes `RoomOptions.encryption`, AES-GCM frame encryption, shared/per-participant keys, encryption-state callbacks, and key-slot controls. Use the SDK implementation; do not implement a new media cipher. Both exact-resolution video tracks and the single shared-audio track must be encrypted before publishing. The SFU can forward and switch subscriptions without decrypting media.

The desired trust boundary is that the Ubuntu SFU and our token service cannot decrypt screen content or shared audio. Generate a cryptographically random room secret on the creating Windows client. Deliver it to invited clients through a trusted channel independently of server authentication. Do not put it in room metadata, participant metadata, JWTs, server configuration, logs, telemetry, or URLs transmitted to our service. A manually shared random secret is suitable for the initial private-group prototype; convenient authenticated invitations need a separate design and review before release. Do not substitute a short room name or ordinary password for a random key.

Require matching encryption on every client, block publication until a key is installed, and display an error when decryption fails. Never silently downgrade a private room to transport-only encryption. Missing and incorrect keys must produce no usable decoded video/audio while the sender continues transmitting encrypted media. Check the actual SDK publication encryption type as well as successful playback. Cover both qualities, audio, quality switches, late joins, reconnects, and key changes. Benchmark encryption against the same unencrypted controlled fixture to measure overhead; 60 FPS remains a target until measured.

Transport TLS and room access control remain necessary. The server sees participant identities, room membership, track/control metadata, IP addresses, and traffic timing/volume. E2EE protects media content; it does not hide these details or prevent an invited viewer from recording received content. Server-side recording/transcoding would need decryption keys and would expand the trust boundary, so it remains outside the first release.

Membership changes require fresh unpredictable keys delivered only to current members. Deriving a new key from an old group key is insufficient to exclude a removed member who already knows that old key. Define rekey authentication, acknowledgements, late joining, reconnect behavior, and bounded retirement of old keys before claiming member-removal security or forward secrecy. The first shared-secret probe does not implement that group protocol.

Sources: [LiveKit encryption overview](https://docs.livekit.io/transport/encryption/), [C++ E2EE API](https://docs.livekit.io/reference/client-sdk-cpp/e2ee_8h_source.html), and the pinned SDK's local `include/livekit/e2ee.h` and `room.h` headers.

## Local implementation evidence

The native harness now tests matching and wrong keys for both video qualities and associated audio. Encrypted-publication labels alone proved insufficient during startup: one wrong-key run detected part of the known audio tone. The harness now primes only synthetic black video and silence, waits for all three sender encryption-OK events, and requests fresh video keyframes before beginning content. A bounded timeout aborts publication of test content. Apply the same gate before feeding actual captured video/audio when app publication is implemented.

Wrong-key checks retain the original global tone threshold and add overlapping short-window checks; no decoded content video is permitted. Preroll is explicitly flagged and separately counted. See [the mismatch/startup report](09-frame-metadata-fix.md) for measurements and remaining limits. This is a local feasibility check, not validation of production invitations, rekeying, or audited group security.

The subsequent [fail-closed cryptor increment](20-fail-closed-cryptor.md) confirms and blocks native server-trailer and disabled-mode plaintext bypasses for encrypted tracks, removes raw reception from the production receiver API, and tests actual SDK encryption disabling during publication. Historical raw failures remain unresolved, and a new H.264 timestamp round-trip edge is recorded as failed. Whole-app release/security readiness remains open.

The [cryptor parser follow-up](21-cryptor-parser-repair.md) fixes the reproduced H.264 timestamp, wrap/escaped-SSRC and long-header cases while preserving authentication rejection. This resolves that identified native parsing failure in the new engine; it does not resolve historical raw audio anomalies or complete the whole-app release gate.

[Closed receiver startup](23-closed-receiver-startup.md) adds a native guard before asynchronous room setup, detached metadata assembly and explicit activation after the per-track listener exists. Encrypted announcements without local crypto configuration stay closed. Wrong-key and unconfigured-viewer tests admit zero video/audio in the bounded fixtures, and repeated delayed startups have no inspected corruption or decoder diagnostics. Final presentation/playback, in-flight revocation, production key lifecycle and explanation of historical raw-audio failures remain required; this increment does not complete the whole-app E2EE release gate.
