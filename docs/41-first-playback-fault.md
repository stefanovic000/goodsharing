# First playback fault and bounded audio-delay experiment

Date: 2026-10-22, Europe/Budapest. This increment changes diagnostics in the installed app and tests a separate, unpromoted audio-engine variant. Normal UI audio remains disabled. Capture uses the owned local fixture window and generated stereo tones.

## Preserve the first fault

The previous sixteen-entry reset ring loses the initial cause during a longer recovery sequence. With `GOODSHARING_TEST_AV_TRACE` enabled, the adapter now retains the first recorded timing reset after media commits, including up to 128 preceding timing events. This snapshot is immutable for the session; later events continue through the existing bounded rings. It contains timing/count metadata, not audio or screen payloads. The additional snapshot allocates only on a fault with diagnostics enabled. Normal runs do not allocate it or read the extra diagnostic clocks.

The trace records short endpoint discontinuities and presentation-age resets as well as the existing audio/video/render timing resets. It adds the interval between pumps, time since the last device commit, preparation duration and the endpoint's reported short gap. A native control commits permitted PCM, forces a 7 ms endpoint discontinuity, then generates twenty-four later recovery resets. The first event and its preceding context must remain unchanged even after the last-sixteen ring fills. A separate control requires no first-fault history with diagnostics disabled. All 22 native tests pass.

The first longer original-SDK cancellation observation fails, retaining its original assertions. The preserved first reset is an audio headroom reset, from serial three to four after 187,189 media frames. Its sender clock is valid with ten reports and epoch one. The latest pump interval is 2.019 ms and the previous commit is 8.637 ms old. The incoming audio deadline is only 1.614 ms ahead of receipt, completing three consecutive blocks below the existing 10 ms headroom threshold. In the preceding transition, about 10.177 ms passes between callbacks while the mapped source timestamp advances about 5.459 ms. The nearest one-second mean jitter-buffer delay is 38.43 ms with a 40 ms target; later means reach 100 ms. This identifies the first reset in this observation without assigning every historical gap to the same cause.

## Isolate an upstream delay limit

The pinned NetEq API exposes a maximum-delay configuration separate from packet-count capacity. A diagnostic engine variant adds an opt-in 40 ms maximum using that existing configuration. The installed SDK, its patch inputs, frame cryptors, receiver clock validation, app presentation horizon and endpoint limits stay unchanged. The experiment is not a production policy.

The builder verifies the prepared receiver source and original WebRTC archive, builds offline from the existing pinned Cargo lock/toolchain and restores the exact receiver-source bytes in a `finally` block. It writes the derived engine into a separate directory, never installing it into the SDK. The test runner verifies all prepared source hashes after restoration and identifies both original and experimental engine hashes. Other client DLLs must match the installed build byte-for-byte. Both comparison arms use the same diagnostic app and experimental engine; only the maximum-delay setting changes. The engine must acknowledge that setting in the actual viewer log.

The bounded comparison runs four 58-second cancellation observations in default/40/40/default order, then a 40 ms wrong-key case. It retains every outcome under the existing startup, coverage, stereo, whole-session gap, switch, quiet-after-stop and permission checks. These generated-tone tests do not apply a silence detector to ordinary application audio. A separate focused regression set uses the original SDK/default reporting for longer cancellation, source closure during warmup, wrong keys, intentional rendering stall and static-to-motion recovery.

## Results

The final native build passes all 22 tests. The focused original-SDK/default-reporting set passes **3/5** cases: wrong keys, intentional render-stall recovery and static-to-motion recovery. Longer cancellation and source closure during candidate warmup still fail. The longer cancellation observation again records sustained audio headroom loss first, with later mean jitter-buffer delay reaching 70 ms. The source-exit observation records audio arriving after video ingress has aged beyond the unchanged 150 ms lifetime. The adapter correctly fences the stale timeline; continuity acceptance remains failed.

The same-binary diagnostic comparison passes **2/5** cases: its first default-delay cancellation and its capped wrong-key case. The default pass has a 5.979 ms maximum quiet interval. The second default observation fails and first records an 80 ms presentation-age expiration. Both 40 ms cancellation observations fail and first record a one-microsecond negative endpoint lead, requiring the existing underrun recovery. One subsequently times out waiting for sender shutdown; the other loses its active share and fails exit/coverage/stereo/presentation checks. These observations do not establish that the cap causes every later transport failure, particularly because a default run also fails.

The requested maximum does not establish the desired measured bound: one capped observation's interval mean audio jitter-buffer delay still reaches 80 ms. Its configured value alone is insufficient evidence of low end-to-end latency or reliable output. **The 40 ms policy is not adopted.** The installed SDK and all normal latency/permission defaults remain unchanged.

The timeout also exposes a comparison-runner error: incomplete transport results do not always contain a `checks` dictionary. The corrected runner handles missing checks and viewer output while keeping the original timeout failed. It copies the first two attempts into a new indexed continuation without rerunning or overwriting them, then completes the remaining planned cases. Original errors and source hashes are retained. An offline control confirms that successful runtime-provenance checks cannot promote that timeout to a pass. Classified analysis reads any available final selection after closure and labels its conclusions as inferred from the retained fields; it does not invent an upstream cause.

## Remaining acceptance

Final outcomes and archives are recorded alongside this report. A small same-PC comparison cannot establish Internet behavior, physical speaker/display sync, long drift or three-share CPU/memory acceptance. The installed app's PCM capacity/residence stays 60 ms, video lifetime 150 ms, common A/V horizon 80 ms, raw endpoint fill target 15 ms and hard endpoint first-sample lead 30 ms. Any experimental jitter-buffer result must be evaluated with its gaps, concealment, source-clock resets and footprint; a lower target alone does not establish a usable demo. No VPS service is deployed and no unrelated application is closed.
