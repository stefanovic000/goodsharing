# Generation-bound receiving

Date: 2026-10-20, Europe/Budapest. This local step-2 increment connects receive ownership to `RoomController`. The Windows UI still previews local capture; actual screen/audio publication and receiving/rendering/playback UI are not integrated. All test media here is synthetic. Step 2 remains in progress.

## Implemented behavior

`RemoteShareCatalog` validates announcements using the same pure validator as the Qt `ShareModel`. It binds authenticated participant identity, share ID, monotonically increasing generation, quality, exact dimensions, screen-share source and GCM publication type. Each SID has one meaning. Old-generation SIDs remain tombstones for the room epoch; later announcements, partial publication, unpublish and owner departure cannot revive a retired generation. Missing requested video/audio rejects the watch instead of inventing a track or silently selecting another quality. The catalog bounds share history at 64 entries, current tracks at 192 and retired SIDs at 512; exhaustion closes the room and requires a fresh join.

`RoomController::watchShare()` takes an exact owner/share ID/generation, one video quality, optional shared audio and bounded media callbacks. It creates one `RemoteShare` selection and permits at most three watched shares. A selection decodes **one** video quality plus its optional stereo audio. The legacy raw subscription/command bridge remains for diagnostic clients; the normal managed path uses the watch API. No CPU/GPU capacity for three simultaneous shares is established by this count limit.

The SDK delegate forwards matching subscribed tracks and per-SID encryption events to that selection. Incoming frames reach callbacks only after successful decryption for the corresponding owner/SID. Unknown owners, unselected qualities and stale SIDs do not grant readiness. A cryptor failure, or a new/ratcheted state after readiness, permanently closes the watch. A separate room admission token also blocks incoming callbacks immediately on room invalidation, notification overflow or leave.

`unwatchShare()`, generation replacement and owner departure close admission immediately. The transport worker closes/joins readers and requests SDK unsubscribe; SDK callbacks only do bounded state/enqueue work. A replacement selection of the same logical share is rejected until the previous watch reports `stopped()`. Pending subscription cancellation waits for its subscription result before unsubscribe, avoiding reuse of a SID while an old request is in flight. Missing subscription/unsubscribe completion has a five-second deadline and fails the room closed. Matching asynchronous subscription failure closes the watch. A late unsubscribe with a different SDK Track object cannot retire a replacement track.

Media callbacks run on reader workers and borrow the frame. They must return promptly and must not call Stop or retain the borrowed frame. A callback already running at revocation can finish; `stopped()` is the completed teardown barrier. A future rendering/audio sink must also reject stale watch/generation handles when presenting queued data, and use bounded/newest-frame storage instead of one queued Qt notification per decoded frame. No end-to-end presentation-age guarantee is implied by callback admission or four-frame queue capacities.

## Remaining work

Manual quality selection currently means an explicit stop and fresh watch. Audio is stopped with that watch; continuous audio across a video-only quality switch is still a step-4 requirement. Automatic fallback, secure invitations/rekey and automatic reconnect/republication are not implemented. A tested explicit leave/rejoin is not a network-outage recovery test.

SDK/network backlog age and congestion recovery, actual WGC/WASAPI publication, GPU scaling/rendering, verified hardware decoding, A/V synchronization and three-share/long-term footprint tests remain open. Earlier startup pixel corruption and lifecycle handle/thread growth failures remain preserved in [the publisher results](14-share-publisher.md); these passing bounded checks do not explain or erase them. Neither the previous five-minute result nor the previous stability evidence is reassigned to this new build.

All test fixtures stayed local. Existing applications/services, games, network configuration, SSH and the VPS were untouched. No game injection, game/render/input hooks, game-memory access, overlay or driver was added. Real CS2/Rocket League capture/coexistence checks remain required once the actual sharing path is usable.
