# Coordinated publisher and per-track encryption

Date: 2026-10-20, Europe/Budapest. This is the second local increment of step 2. The normal Windows app still previews capture; it does not publish it. All media in the checks below is synthetic. The historical extraction measurements are [preserved](13-transport-extraction.md).

## Implemented ownership

`RoomController` now owns a one-shot `SharePublisher` on its transport worker. The publisher owns both exact-resolution hardware H.264 outputs and optional 48 kHz stereo audio. Names bind the two qualities and audio to one share ID and generation. Start, readiness, sharing, Stop and failure have explicit states. Stop closes content admission immediately, then unpublishes known tracks and releases sources/encoders on the owner thread. Normal Stop keeps the room joined. Failed setup rolls back completed publications; a controller-level publication failure closes the room to clean up uncertain SDK state. Cancellation before/during setup and room leave cannot reopen the old input handle.

`ShareInput` accepts only a ready generation. It holds one newest raw video pair; replacing a waiting raw frame does not discard an accepted encoded reference frame. Video must be correctly sized, monotonic, non-priming and no older than 150 ms. Audio accepts exact 10 ms stereo blocks, with a 100 ms queue/age limit; overflow fails closed. An owned audio handoff worker now drains audio independently of video MFT/pacer waits, checks the same per-track gate before every handoff, and joins before source unpublication/destruction. The earlier owner-tick implementation could starve audio; the failed sustained run below motivated this change. The capture integration must normalize Windows capture timestamps to the steady-clock time base used here. These bounds do not measure the SDK's entire RTP/network backlog.

## Encryption boundary

Initial verified-receiver runtime SHA-256: wrapper `2171c3db4688b65d55b09aaaa5e3e3f208ce1492367cf280eb5950aa0a324537`, engine `95834da0838c1493a5c14e3c0893c48127135aff1a1a69b7e3e1ca0ad7129902`. C++ patch `704fbaac70c8a7a931765728d6ca7e1b769851672c74f6d25198b1a1862e5462`; engine patch `44d88a5b4978a96de625cb83e0dd882b7bdc2accd54e17fa0e2ee629d925dff4`. Older reports retain their own earlier runtime hashes.

The pinned Rust engine, FFI protocol and C++ wrapper now propagate the exact track SID on encryption-state events. The protocol extension is optional field 3; the installed wrapper event header and both DLLs are included in provenance verification. `EncryptionGate` binds readiness to the authenticated local owner and every SID in the completed publication manifest: two with audio off, three with audio on. Repeated events for one track cannot substitute for another. Before readiness, only internal synthetic black/silence is submitted. The captured-input API cannot mark content as priming.

Readiness times out closed. Failure, Stop, room invalidation, or a cryptor returning to a non-ready state after complete readiness permanently closes that generation. A later OK does not resume it. Video checks permission before encoding and again immediately before handing encoded bytes to the SDK; audio checks immediately before submission. Reconnection requires explicit fresh room/share setup; automatic recovery is not implemented.

`ShareReceiver` now requires successful decryption for the authenticated owner and exact remote SID before creating a decoder stream or admitting its callbacks. Failure/unsubscribe closes admission immediately and tears down readers on its control thread; a later OK cannot revive the revoked SID. State is bounded to 128 entries, including early events/tombstones; pending attachments to 16, commands to 64 and active readers to eight. One instance belongs to a room/share generation. Connecting the remote model/generation lifecycle to these receivers remains integration work. The older independent SDK probes explicitly retain diagnostic raw reception so they continue testing SDK behavior without this guard.
