# Fail-closed cryptor hardening

Date: 2026-10-21, Europe/Budapest. This increment prioritizes the user's mandatory E2EE failure contract. All fixtures use synthetic content on this Windows PC. The UI still only previews local capture. This is bounded hardening and evidence, not a zero-bug guarantee or a completed security audit.

## Confirmed native behavior

The focused test links the exact pinned `webrtc-89d790b` static library. Its control variant deliberately uses the upstream cryptor/key provider, independently of app receive admission, RTP transport, decoders and packet-loss concealment (PLC). It checks synthetic audio payloads and H.264-framed bytes at the cryptor output; it does not claim those native unit payloads are independently decoded pictures or sound.

The control forwards a nonempty, unencrypted payload when it carries the configured server-injected-frame trailer. It also forwards plaintext in both sender and receiver directions after disabling the cryptor. Empty input is forwarded without authentication as well. Correct-key encrypted round trips are positive controls; wrong-key, missing-slot, tampered and truncated inputs are negative controls. The [native policy report](../artifacts/20261021-150556-cryptor-policy/summary.json) records the library and executable hashes and all four audio/video control/strict results, without saving keys or payloads.

The published [WebRTC cryptor source](https://raw.githubusercontent.com/webrtc-sdk/webrtc/m150_release/api/crypto/frame_crypto_transformer.cc) documents disabled-mode passthrough and server-injected-frame handling. That moving branch is not a substitute for the pinned binary: the binary control above directly demonstrates its behavior. The branch now has additional checks that must not be assumed present in this pinned release.

These native findings establish real bypass behavior, but do **not** establish the exact cause of every earlier wrong-key PCM/tone failure. Those old failures remain preserved and unresolved in [the publisher evidence](14-share-publisher.md).

## Dedicated app policy

`patches/strict_frame_cryptor.h` is shared by the focused native test and the reproducible engine patch:

- `StrictKeyProvider` never installs a server plaintext trailer. Even nominal server-generated black/silence frames must not bypass authentication. It sets the retained empty-frame-discard option after construction: the pinned options copy constructor omits that member, so setting a temporary options object alone is insufficient.
- `StrictFrameCryptor` initializes its underlying transformer with encryption enabled. A disable request permanently revokes new work instead of entering upstream plaintext passthrough. Re-enabling the same cryptor cannot reopen it; a fresh lifecycle is required. Already queued transformer work retains encryption/authentication rather than switching to passthrough.
- The existing per-owner/SID/generation publisher and verified-receiver gates remain required. Synthetic black/silence primes startup; captured content cannot mark itself as preroll. The strict cryptor supplements these gates instead of replacing them.

This uses the existing SDK AES-GCM implementation. It adds no image queue, per-frame payload copy or worker of its own; the native cryptor already owns its worker. This is an implementation property, not a measured CPU/RAM improvement or proof of constant total resource use.

The production `ShareReceiver` API no longer has a `DiagnosticRaw` mode or a verification-disable constructor. Raw SDK regression readers are isolated in `tools/diagnostic_track_readers.h`, compiled only into diagnostic probes. This helper has bounded commands/readers and runs stream construction off SDK callbacks. Shipping/package checks must still exclude diagnostic probe executables, including unencrypted test modes. The normal UI currently links capture/preview rather than exposing those probes.

## Native verification and an additional failure

[Eight native checks](../artifacts/strict-cryptor-final-ctest.log) pass. In both audio and H.264 policy tests, valid encrypted bytes round-trip before and after hostile inputs; zero hostile inputs reach the strict output callback. Missing sender keys produce no output. Disabling/re-enabling the strict sender and receiver does not resume their outputs. Known-good completion sentinels and worker teardown avoid treating an arbitrary sleep with no callback as proof of rejection.

The first H.264 fixture failed. Additional checks isolated a separate **unresolved valid-round-trip edge**: with small RTP timestamps, the receiver fails to return even the first known-good packet before any hostile input. It fails with both the upstream and strict cryptors. The [upstream edge log](../artifacts/strict-cryptor-rtp-edge-control.log) and [strict edge log](../artifacts/strict-cryptor-rtp-edge-strict.log) retain these failures; `goodsharing_cryptor_test --video --rtp-edge` reproduces the strict case. The earlier [native run](../artifacts/strict-cryptor-ctest.log) remains a failed eight-test run. Ordinary-timestamp cases pass the same authentication assertions. This is not classified as a privacy leak, but the valid-frame loss is still a correctness issue, not a successful edge test. Its exact cause and relation to historical startup corruption are not established.

The [combined final native diagnostic report](../artifacts/20261021-151606-cryptor-policy/summary.json) explicitly has `policy_rejection_passed: true` and **`passed: false`** because both edge round trips fail with exit code 1. Run `scripts/test_cryptor_policy.py --with-edge-diagnostics` to retain both passing rejection controls and failing edge cases. The ordinary-timestamp eight-test CTest suite does not include this known failing diagnostic; it must not be presented as all crypto cases passing. Its native key-provider control uses failure tolerance -1 so a failed authentication cannot prevent the subsequent known-good completion sentinel; production publisher/room tests use failure tolerance 0 and sticky app admission revocation.

The [engine build](../artifacts/strict-cryptor-engine-build.log) passes the source-level Rust shutdown regression and builds the final DLL. Build-time SDK verification now also requires SHA-256 provenance for the strict-policy header. The engine is `c79d28e77a38fb3d3e21ffe4faa144277ee916e716f83093f02feeaebd060c7f`; its cumulative Rust patch is `851284c50d73a44111bf9f716770fa78aab85b3144534780b6fb49da5ffbbc10`. The C++ wrapper remains unchanged. The current publisher probe is `7537eb3e8d4e9552fcbd465a6f6314dd36300a0cd0ddea043a741550f551dcf6`.

## App-level verification

[All nine publisher scenarios](../artifacts/20261021-150834-share-publisher/summary.json) pass, retaining the eight previous cases and adding a real SDK `disable-encryption` fault. After approximately 1.5 seconds of valid sharing, that case disables the publisher E2EE manager without manually injecting an app gate failure. The publisher reaches Failed, closes its gate/input, and records zero observed video handoffs after revocation. Re-enabling the manager and ticking the same publisher does not resume the failed share. This is not a claim that previously authorized, already delivered content can be recalled, or a measurement of every in-flight audio packet.

The separate [strict wrong-key app check](../artifacts/20261021-151007-share-publisher/summary.json) requires **zero admitted video frames including preroll, zero audio sample frames and zero verified tracks**. Both qualities remain blocked. The sender still transmits encrypted content; ciphertext/signaling traffic is not plaintext exposure.

[Managed receiving](../artifacts/20261021-151014-remote-share/summary.json) passes normal and wrong-key cases, variable 55/45/30/60 FPS, quality reselection, generation replacement, cancellation and teardown. [Room control](../artifacts/20261021-151032-room-controller/summary.json) passes eight cycles, owned publication restart, idle/wakeup and cleanup. These bounded passes do not classify historical lifecycle resource growth.

The [independent raw stereo suite](../artifacts/20261021-150641-stereo/summary.json) passes all six cases, including actual owned playback/process-loopback, mono control, unencrypted diagnostic control and wrong-key reception. Two further raw wrong-key checks also pass: [first](../artifacts/20261021-150717-stereo/summary.json), [second](../artifacts/20261021-150724-stereo/summary.json). Their overlapping 100 ms tone maxima are approximately 106.10, 0 and 0, respectively, under the unchanged 200 limit. Raw decoder/PLC output still contains sample frames; low tone measurements are not a claim of authenticated silence or zero exposure in a raw API. Production admission is verified separately above. Passing repeats do not erase the old raw failures.

## Remaining verification

The final [clean encrypted relay run](../artifacts/20261021-151143-network-media/summary.json) passes: 1,080 inspected live content frames per quality, no inspected pixel/metadata/dimension errors, correct stereo and independently decoded source recordings. Source-to-decoded p95 is 30.27/25.72 ms at 1080p/720p. This is a short synthetic one-PC result, not a capture-to-display or Internet measurement.

The [50 ms FIFO restriction](../artifacts/20261021-151209-network-media/summary.json) still **fails continuous delivery**: longest gaps are 5,113/2,351 ms at 1080p/720p, with only two/three inspected pressure-period frames. Pressure p95 passes on those tiny samples, while 720p maximum age is 2,380 ms; these are not healthy playback results. The [1,000 ms FIFO restriction](../artifacts/20261021-151233-network-media/summary.json) **fails age and continuous delivery**: pressure p95 is about 717 ms for both qualities, 1080p has a 3,122 ms gap and does not reach the observation tail. Both runs pass inspected media correctness, independent source decoding, stereo tone checks, measured rate restriction, sender/receiver route verification, stage age checks and owned cleanup. Pressure-time audio continuity remains unproven. No controlled latency improvement is inferred from different runs' rates or feedback histories.

[Encoded-output recovery](../artifacts/20261021-151436-share-publisher/summary.json) passes the 200 ms intentional stall: one stale frame is rejected and one fresh-keyframe recovery completes per quality, with 501 submitted audio blocks and 10 ms mailbox high-water. [The 250 ms owner-stall run](../artifacts/20261021-151446-share-publisher/summary.json) also passes independent decoding and audio draining: 1,001 blocks and 10 ms mailbox high-water over ten seconds. These fault runs are not sustained-60-FPS gates.

The owner-stall [resource trace](../artifacts/20261021-151446-share-publisher/stereo-footprint.json) includes synthetic generation, hardware encoding, software decoding of both qualities, content inspection and in-memory recordings. Its sampled lifetime averages 9.93% of 12 logical processors / 1.191 core equivalents; peak working set is 149.02 MiB and peak private commit 235.15 MiB. This short workload does not establish a steady app budget, improvement, three-share capacity or leak-free result. Current joined-idle room CPU is 0.221% of 12 logical processors over approximately ten seconds; wake completes in 1.25 ms and owned publisher Stop peaks at 209.55 ms. Historical resource-growth failures remain open.

The [provenance check](../artifacts/strict-cryptor-provenance-check.json) verifies recipe idempotence, the exact strict-header input and matching dependency-lock/installed/runtime hashes; Ninja reports no pending work. The [final process audit](../artifacts/strict-cryptor-final-process-check.json) finds zero owned probe/SFU processes without stopping any process. The [frozen results and source archive](../artifacts/20261021-strict-cryptor-validation.json) keep this engine separate from prior snapshots and preserve both passing component results and failed gates. No earlier engine's latency or resource measurement is assigned to this DLL.

The whole-app E2EE release gate remains **open**: historical raw failures and the new H.264 timestamp edge need investigation; production invitations, membership rekey/reconnect and real capture-to-final-presentation/playback need validation. An already-running authenticated callback may finish during revocation. Future rendering/playback must recheck current generation/permission at consumption, discard queued data and clear/mute on failure. No usable room sharing UI exists yet, and no guarantee about that unfinished path is implied by backend checks.

The previously failed upload-pressure latency gate, hardware decoding, three-share capacity and long-term CPU/RAM/lifecycle stability are also unfinished. All testing stays local; games, unrelated apps/services, SSH and the VPS remain untouched.
