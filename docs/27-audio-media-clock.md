# Audio media-clock investigation

Date: 2026-10-21, Europe/Budapest. Local work authorized by “continue”. Remote sound playback remains disabled. This increment adds timestamp plumbing and measurements; it does not claim synchronized playback.

## Implemented

The reproducible SDK preparation now carries optional audio `capture_time_ms` and `sink_time_us` from WebRTC's native sink through the Rust audio frame, FFI buffer information and C++ `AudioFrameEvent`. Capture time is supplied only when WebRTC supplies it. Sink time is sampled on WebRTC's native clock before FFI/reader queues. Generated, filtered or rebuffered PCM whose original timing is not proven retains absent timing. Existing stereo options and encryption permission checks remain in place.

`scripts/audio_timing_patch.py` owns the shared audio wire extension and engine transformations. Both SDK preparations use the same protocol definition. Cumulative source patches and dependency hashes are regenerated from the pinned pristine source archives. No cryptor policy, parser, encryption algorithm, bitrate policy or application capture path changed. The SDK binaries do change and require the matching rebuilt application/probes.

The synthetic publisher records optional audio timing beside its existing bounded amplitude-code trace and records public video timestamps beside independently decoded video identities. `analyze_media_clock.py` identifies audio content independently, compares corresponding content positions on the candidate SDK audio/video timelines and rejects absent, zero, unrelated or offset clocks. It never fills missing timing from callback arrival. Four offline controls cover a valid common receiver clock two hours away from the source app clock, an unrelated video clock, a 300 ms audio offset and absent audio timestamps. The preceding nine audio-content/held-image diagnostic controls remain passing.
